1. Members
----------

PRAXIS-CTL-02 Typed control-plane read API for work state and legal actions
  (PRX-CTL-005, PRX-CTL-011). Depends on: -
  1. versioned, documented JSON contract in the F# contracts for the work
     list and one work item: identity, semantic state, recorded backlog and
     live state, legal next actions, and for refused transitions the
     kernel's reason where it can say why
  2. obligations and unknowns where Praxis records them; explicitly
     unavailable (not empty) when no source exists
  3. read endpoints never write repository state
  4. unknown item -> 404 with a structured error body
  5. existing /api/work clients keep working or the change is documented
  6. tests

PRAXIS-CTL-03 Read API for executions, receipts and evidence
  (PRX-CTL-005, PRX-CTL-011, PRX-CTL-012). Depends on: CTL-02 envelope
  1. typed, versioned endpoints list executions (optionally per work item)
     and show one: role, status, actor; provider/model/runtime presented as
     execution-host information, never as owner of work state
  2. an execution's steps with expected and observed receipts and their
     match / mismatch / indeterminate state
  3. a work item's recorded evidence and durable checkpoints
  4. telemetry usage and cost where recorded, explicitly unknown otherwise
  5. obtained through the same paths as `execution show --json`,
     `work context`, `work checkpoint show`, `telemetry usage`; not re-derived
  6. endpoints never write; tests

PRAXIS-CTL-04 Transition requests with structured refusals
  (PRX-CTL-006, PRX-UI-024, PRX-UI-027). Depends on: CTL-02 item view
  1. one transition-request endpoint (ready, block, abandon, start, resume,
     complete with their arguments) executed through the CLI's own
     transition path, never reimplementing a rule
  2. success returns the item's resulting typed state
  3. refusal -> structured refusal (machine-readable category, kernel's
     message, requested action), appropriate HTTP status, Praxis state
     byte-for-byte unchanged (test)
  4. actor identity / provenance are those of the equivalent CLI command,
     never inferred from the HTTP client
  5. existing per-action routes keep working or are documented as
     superseded; tests

PRAXIS-CTL-05 Host holds no canonical state; reconstructs on restart
  (PRX-CTL-004, PRX-CTL-008, PRX-UI-009). Depends on: CTL-02..04 endpoints
  1. no workflow state in the host: every response derived from durable
     records at request time (or a fingerprint-invalidated cache)
  2. responses carry the state fingerprint and repository/commit identity
  3. test: restart (new instance, same repo) -> identical responses; test:
     CLI changes state while host runs -> change observed without restart
  4. automated check fails if the host writes repository files other than
     through the CLI transition path
  5. documented

PRAXIS-CTL-06 Multi-repository aggregation without a central store
  (PRX-CTL-007). Depends on: CTL-02 (per-repository contract)
  1. hub typed read endpoints: registered repositories with availability,
     each repository's work list and work item, by delegating to that
     repository's own Praxis CLI with the same per-repository contract
  2. hub persists only registration data; test shows a state change in a
     registered repository appearing without hub involvement
  3. unreachable / incompatible repository reported for that repository,
     never failing the whole response
  4. any hub mutation delegated to the owning repository's transition path
  5. docs/project-administration-hub.md updated; tests

New abstractions and why existing ones do not fit:
- ControlPlaneJson (contract): no versioned control-plane schema exists
  (search above). The legacy `work show` row is unversioned and must stay
  byte-compatible for existing /api/work clients, so it cannot be changed
  into the new contract.
- `praxis control-plane ...` (read-only CLI command group + one transition
  request): needed so that the hub can obtain the same per-repository
  contract from a spoke by running its own CLI (CTL-06.1); `hub work` only
  relays raw `work list` rows (Hub.fs:364) and has no envelope/fingerprint.
- State fingerprint: no existing function hashes Praxis state; Ordo's
  StateFingerprint (Model.fs:223) is a caller-supplied value of an
  observation, not a digest of `.ros/`.


3. Group-level design
---------------------

Common architecture and shared invariants
- One read-only CLI command group is the single producer of every
  control-plane document:
    praxis control-plane work [--tag T]* [--status S]   (work list)
    praxis control-plane work ID                         (one item)
    praxis control-plane evidence ID                     (evidence + checkpoints + usage)
    praxis control-plane executions [--work-item ID]     (execution list)
    praxis control-plane execution EXE-ID                (one execution)
    praxis control-plane source                          (identity + fingerprint only)
    praxis control-plane transition --id ID --action A [args]   (the only mutation)
  It reads through the same in-process functions the corresponding CLI
  commands use (readShowView, readContextView, checkpoint show document,
  execution snapshot document, telemetry usage document).
- The web host (`web serve`) answers /api/v1/... by running
  `control-plane ...` through CliProcess.runSelf, exactly as the legacy
  routes already run `work ...`; the hub answers its /api/v1/... by running
  each spoke's own `./praxis control-plane ...` through Hub.runSpoke.
  Neither host parses or reshapes the per-repository document beyond
  wrapping it in the hub's per-repository envelope.
- Every document is an envelope:
    { "schema": "praxis.control-plane", "schemaVersion": 1, "kind": K,
      "source": { repository, commit, branch, stateFingerprint },
      "data": ... }   or   "refusal"/"error": { category, message, ... }
  Invariant: data is derived at request time from durable records; no
  host-held state; no timestamps of the request are embedded (so a restart
  yields identical bytes).
- Availability wrapper for optional sources:
    { "status": "available", "value": ... } |
    { "status": "unavailable", "reason": "..." }
  Used for obligations, unknowns, usage, checkpoints of backlog-only items.

Conflicting requirements, and how each is resolved
- CTL-02.5/CTL-04.5 (keep legacy clients) vs a typed contract: new
  versioned routes under /api/v1; legacy /api/work routes keep their exact
  behaviour and are documented as superseded, not removed.
- CTL-04.1 "same transition path, no rule reimplemented" vs CTL-04.3
  "structured refusal category": the category is never inferred from
  stderr text. Before executing, the request is checked against the
  kernel's own decision functions (BacklogTransition.decide /
  WorkTransition.decide) over the recorded state -> `illegal-transition`
  or `missing-argument`, with the kernel's rejection code. A legal request
  runs the unchanged CLI command line (WebInterface.commandLine) as a
  child process; if the CLI still refuses (a guard the decision functions
  do not model, e.g. durable-checkpoint or evidence-file checks) the
  category is `rejected` and the message is the CLI's own. Unknown id ->
  `not-found`; unusable request -> `invalid-request`.
- CTL-04.4 identity vs existing per-action routes accepting `actor` from
  the body: the v1 transition endpoint takes no identity input; the child
  CLI resolves identity from the host process environment exactly as the
  same command typed in that shell would. Legacy routes unchanged.
- CTL-05.1 "derived at request time" vs response cost: no cache at all
  (the simplest reading of the criterion); each request is a fresh CLI
  process, as legacy routes already are.
- CTL-05.4 "host never writes" vs the hub writing its registry and the web
  host writing temporary upload files: the check scopes "repository files"
  to the served repository (web) and to registered spokes (hub); the hub's
  own registration data under its root is the one permitted hub write
  (CTL-06.2), uploads go to the OS temp directory.
- CTL-03.1 "executions" has two recorded notions: Ordo execution envelopes
  (.ros/executions, carry role and receipts) and telemetry executions
  (.ros/telemetry/executions, carry usage). Executions endpoints present
  envelopes (the `execution show --json` path named by CTL-03.5); telemetry
  executions appear in the evidence document's usage section.

The one design that serves several members
- Contract module (Ros.Contracts/ControlPlane/ControlPlaneJson.fs): envelope,
  source identity, availability, refusal/error categories, HTTP status
  mapping (pure), legal-action view. Serves CTL-02, 03, 04, 05, 06.
- Error model: one category set {not-found, invalid-request,
  illegal-transition, missing-argument, rejected, unavailable,
  incompatible} with one HTTP mapping (404, 400, 409, 422, 422, 503, 502).
- Transaction boundary: the CLI transition command is the only mutation; a
  refused request performs no write (pre-check) or is refused by the CLI
  under its own lock (which already guarantees no partial write).
- Source identity / fingerprint (CTL-05) computed by the CLI, so the hub
  obtains a spoke's identity by delegation, not by reading spoke files.

Where one design cannot serve all
- Hub availability (CTL-06.1/.3) is a hub-only concept (path exists,
  launcher exists, contract version compatible); it wraps rather than
  extends the per-repository contract.
- Execution legal actions are already computed by LegalActions.compute in
  `execution show`; they are relayed, not unified with work-item actions.

Compatibility constraints and migration implications
- `execution show --json` gains an additive `observations` array per step;
  `telemetry usage` output unchanged (builder moved, bytes identical);
  `work checkpoint show --json` unchanged (builder extracted).
- Legacy /api/work, /api/work/ID, POST /api/work/ID/ACTION and hub /api/work
  unchanged. No data migration: nothing new is persisted.
- An older spoke without `control-plane` exits non-zero with usage text:
  reported per repository as `incompatible`.

Common tests
- Contract unit tests (envelope, availability, refusal mapping, legal
  actions from kernel decisions).
- CLI tests for each control-plane command over a fresh repository.
- HTTP tests through ServedProcess: v1 reads, 404 body, transition success
  and refusals with byte-for-byte .ros comparison, restart identity, live
  change visibility, no-write check (repository tree digest before/after
  every read endpoint), hub aggregation with a broken spoke.

Risks of solving each member independently
- Five different envelopes/error shapes (one per item) and a hub that
  reshapes a second copy of the per-repository contract (CTL-06 violating
  "same contract").
- CTL-04 inventing refusal categories by parsing stderr, diverging from
  CTL-02's legal-action reasons for the same kernel decision.
- CTL-05's fingerprint bolted on after the fact, changing CTL-02/03 shapes.

Shared infrastructure attribution (PRX-GRP-043)
- ControlPlaneJson envelope/availability/source and the `control-plane`
  command skeleton: attributed to PRAXIS-CTL-02 (first consumer) and named
  in every commit message of the items it serves.
- Fingerprint/source identity: PRAXIS-CTL-05.

--------

   routes (CTL-02, with CTL-05.2 source fields). Milestone checkpoint M1.

   executions|execution|evidence` + routes (CTL-03). Checkpoint M2.

   Checkpoint M3.

5. Hub /api/v1 repos/work/item/transition delegation; docs (CTL-06).
   Checkpoint M5.
6. Verification pass per criterion (section 5), completion per item.
