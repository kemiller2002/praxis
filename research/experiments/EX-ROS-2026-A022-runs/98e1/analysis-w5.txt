Architecture analysis: PRAXIS-CTL-06
=====================================

Item: PRAXIS-CTL-06 "Multi-repository control-plane aggregation without a
central store" (./praxis work show PRAXIS-CTL-06)
Requirement: PRX-CTL-007 (requirements/EXECUTION-ORCHESTRATION.md:329) --
"A local control plane MAY aggregate multiple repositories for discovery and
navigation, but aggregation MUST NOT silently move canonical repository work
state into a central proprietary store."
Depends on: PRAXIS-CTL-02 (complete) -- its per-repository contract
`praxis.work-state` v1.
Base commit: ed4101be (PRAXIS-CTL-05 completed on this branch).


1. Item and acceptance criteria
-------------------------------

| # | Criterion (from the backlog description) |
|---|---|
| 1 | The hub exposes typed read endpoints listing registered repositories with their availability, and each repository's work list and work item, by delegating to that repository's own Praxis CLI and using the same per-repository contract as the single-repository API. |

| 3 | An unreachable or incompatible repository is reported for that repository and does not fail the whole response. |
| 4 | Any mutation offered through the hub is delegated to the owning repository's transition path. |
| 5 | docs/project-administration-hub.md updated; tests. |

New abstractions and why existing ones do not fit:
- `SpokeAvailability` (available | unreachable | incompatible | unreadable):
  the legacy aggregation reports a free-text `error` row (Hub.fs:231) and
  `repoSource.unavailable` (Hub.fs:226); neither distinguishes "cannot run
  its Praxis" from "runs a Praxis that does not speak praxis.work-state v1",
  which criterion 3 names separately. Searched `grep -rn "Unreachable\|Incompatible" src`:
  only installation/remote concepts, unrelated.
- `praxis.hub-state` v1 envelope: the hub must say which repository a
  document came from, that repository's availability and source identity,
  and must not alter the spoke document. Adding fields into the spoke's
  `praxis.work-state` document would make it no longer the spoke's
  document, and ControlPlaneSource would overwrite its `source`. A
  wrapper envelope keeps the per-repository document intact.
- CLI `work state [ID] [--tag T]* [--status S]` and
  `work transition --id ID --request JSON`: today the work-state contract
  exists only inside `web serve`, so a hub could only obtain it by
  starting an HTTP server in every spoke or by reading spoke files (both
  forbidden by the hub's one rule). These commands are thin wrappers over
  the existing pure functions above.


3. Invariants and shared infrastructure
---------------------------------------

- The hub never reads or writes a registered repository's files; every
  spoke interaction is that repository's own launcher (docs/project-administration-hub.md
  "The one rule"). New code goes through invokeSpoke only.
- The hub host writes nothing; registry mutation stays `praxis hub
  register|unregister` (HubWeb.fs:95-114). Enforced by the host source check.
- The hub keeps no state between requests (PRAXIS-CTL-05). Every v1 hub
  response is computed from the registry and the spokes at request time.
- One per-repository contract: what the hub returns as a repository's work
  list/item is exactly what that repository's `GET /api/v1/work[/ID]`
  returns (same pure stateResponse, same version).
- Transition rules live only in the owning repository (WebInterface.transition
  in the spoke's own CLI process).
- Identity/provenance of a transition is that of the spoke CLI run in the
  hub's environment, never inferred from the HTTP client (same as
  PRAXIS-CTL-04's single-repository rule).
Shared infrastructure touched: CliProcess, ControlPlaneSource (unchanged),
WebInterface (one pure inverse function added), Program.fs dispatch/usage.


4. Design
---------

4.1 Spoke CLI (contract producers, in every repository's own Praxis)
- `praxis work state [--tag T]* [--status S]` -> praxis.work-state
  `work-list` (stdout, exit 0).
- `praxis work state ID` -> `work-item` (exit 0) or praxis.error
  `work-item-not-found` (stdout, exit 1); unreadable state -> praxis.error
  `work-state-unreadable` (exit 1). Invalid arguments -> exit 2.
- `praxis work transition --id ID --request JSON` -> the JSON body of
  POST /api/v1/work/ID/transitions; prints `work-transition` (exit 0) or the
  structured refusal (exit 1). Invalid arguments/unparsable JSON -> refusal
  `invalid-request` (exit 2).
File: src/Ros.Cli/WorkStateCommands.fs (after WebInterface.fs).

4.2 Domain/contract
- src/Ros.Domain/Work/SpokeAvailability.fs: DU + `code`, `reason`.
- src/Ros.Contracts/Work/HubStateJson.fs: contract `praxis.hub-state` v1.
  * `classify expectedKinds exit stdout failure` (pure): the spoke answer
    -> {Availability; Document}. praxis.work-state v1 of an expected kind
    with exit 0 -> available + document; praxis.error with exit != 0 ->
    available + error document, except `work-state-unreadable` ->
    unreadable; praxis.work-state of another version -> incompatible
    ("speaks version N; this hub reads version 1"); anything else (older
    Praxis: usage text, exit 2) -> incompatible, naming the command.
  * Renderers: repositoryNode (id, name, path, registeredAt, availability
    {status, reason?}, repositorySource), `repository-list`,
    `repository-work-list`, `repository-work-item`,
    `repository-work-transition` (each {repository, document}), aggregated
    `work-list` ({repositories: [{repository, document|null}]}), and
    errors `repository-not-registered` (404) and `repository-unavailable`
    (502, carrying the repository node).

4.3 Hub effects (src/Ros.Cli/Hub.fs, module Hub)
- invokeSpoke repo args : Result<ProcessResult, string> (unreachable reason).
- readSpoke repo args kinds : SpokeRead {Repo; Answer; Source} -- attributed
  with StateIdentity.stable over the spoke's `state identity --json`.
- repositories root, repositoryWork root id tags status, workItem root id
  itemId, aggregatedWork root repo tags status, transition root id itemId
  requestJson. Unknown repo -> Error (not registered). Each aggregated
  repository is read independently; a failure is that repository's
  availability, never an Error of the whole call.

4.4 Hub HTTP (src/Ros.Cli/HubWeb.fs)
| GET  | /api/v1/repos | repository-list (availability per repository) |
| GET  | /api/v1/repos/:id/work?tag=&status= | repository-work-list |
| GET  | /api/v1/repos/:id/work/:item | repository-work-item |
| GET  | /api/v1/work?repo=&tag=&status= | aggregated work-list |
| POST | /api/v1/repos/:id/work/:item/transitions | repository-work-transition (delegated) |
Status: 200 for documents; a relayed praxis.error gets the status the
single-repository API gives that code (work-item-not-found 404, refusals via
refusalStatus); unknown repository 404; an unavailable repository on a
single-repository route 502 with the repository node; the aggregated and
repository-list routes are always 200 with per-repository availability.
Transaction boundary: one transition = one spoke CLI process; the hub adds
no step before or after it that writes anything.

4.5 CLI parity: `praxis hub state [--repo ID] [--item ID] [--tag T]* [--status S]`
prints the same documents (aggregated, repository or item).

Error model: hub-level problems (unregistered id, bad request) are
praxis.error documents with a hub code; repository-level problems are the
repository's availability or its own relayed document.


5. Compatibility
----------------
- Legacy /api/repos, /api/work, POST /api/repos/:id/work and `praxis hub
  work|repos|create` keep their exact shapes (tests unchanged).
- registry.json format unchanged; nothing new persisted.
- Older spokes keep working on legacy routes and are reported `incompatible`
  on v1 routes (they lack `work state`), with the reason.
- New CLI commands are additive; usage text gains them (docs/cli.md).


6. Tests (tests/Ros.Tests/HubTests.fs, plus allowlist in ControlPlaneHostTests.fs)
- Unit: classify (available, error document, unreadable, version mismatch,
  older Praxis usage text); route table for the v1 routes; inverse refusal code.
- CLI: `work state` list/item/not-found equals `web serve` /api/v1/work output
  semantics; `work transition` accepted and refused (state unchanged).
- Served hub: repository list with availability; per-repository list and item
  equal the spoke's own `work state` output; aggregated list across two
  spokes with one moved (unreachable) and one fake older Praxis (incompatible)
  still 200; state change made via a spoke's CLI visible without any hub
  action, hub root snapshot unchanged and holding only registry files;
  transition through the hub changes the spoke and a refused one leaves the
  spoke byte-for-byte unchanged; unknown repository 404.
- Host source check stays green.


7. Risks
--------
- Cost: each v1 read spawns several spoke processes (identity before/after
  plus the read). Acceptable for a local hub; documented.
- Old spoke incompatibility is detected by output shape, not version
  negotiation; a future v2 contract is reported as incompatible with an
  explicit version reason rather than misparsed.
- `work transition` runs the transition in a child of the spoke CLI (same as
  web serve); identity comes from the hub's environment -- documented, as for
  the single-repository API.
- ControlPlaneSource adds the hub's `source` to hub envelopes; clients must
  use `repository.repositorySource` for the spoke's identity. Documented.
