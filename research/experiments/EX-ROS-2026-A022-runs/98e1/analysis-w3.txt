Architecture analysis: PRAXIS-CTL-04
=====================================

Item:            PRAXIS-CTL-04 "Control-plane transition requests with structured refusals"
                 (`./praxis work show PRAXIS-CTL-04`)
Repository:      kemiller2002/praxis, branch experiment/a022-run-98e1
Base commit:     71a2f6e (PRAXIS-CTL-03: record checkpoint and completion)
Requirements:    PRX-CTL-006, PRX-UI-024, PRX-UI-027 (requirements/EXECUTION-ORCHESTRATION.md:300-328)

1. Item and acceptance criteria
-------------------------------

Obligation: give `praxis web serve` one transition-request endpoint whose
refusals are structured, at API level. Today `POST /api/work/ID/ACTION`
answers a refused transition with `400 {"error": "<CLI stderr text>"}`
(src/Ros.Cli/WebInterface.fs:978-981, `HttpMessages.jsonError 400 message`).

Acceptance criteria (verbatim intent, numbered as in the backlog item):
 1. One transition-request endpoint accepts a requested action for a work
    item (ready, block, abandon, start, resume, complete, with their
    arguments) and executes it through the same transition path as the CLI,
    never reimplementing a rule.
 2. Success returns the item's resulting typed state.
 3. A refused transition returns a structured refusal (machine-readable
    category, the kernel's message, the requested action) with an
    appropriate HTTP status, and leaves Praxis state byte-for-byte
    unchanged, shown by a test.
 4. The actor identity and provenance recorded for an API transition are
    those of the equivalent CLI command and are never inferred from the
    HTTP client.
 5. The existing per-action routes keep working or are documented as
    superseded; tests.

Depends on: PRAXIS-CTL-03 (already on this branch: /api/v1 read routes,
`WorkStateJson`, `WorkStateView`).

New abstractions and why existing ones do not fit:
 - `TransitionRefusal` category type (pure, Ros.Cli): no existing type maps
   "CLI outcome + pre-read action availability" to an HTTP status and code.
   `ActionAvailability.Refused` covers only illegal-in-state; a legal action
   can still be refused by the kernel (missing reason, missing evidence,
   durable-checkpoint guard), and invalid arguments come from exit 2.
 - `WorkOperation.AbandonWork`: the only CLI path that abandons LIVE work is
   `work abandon` (Program.fs:1868-2010); `WorkOperation.Abandon` deliberately
   mirrors the backlog-only route and must not change (criterion 5).

3. Invariants and shared infrastructure
---------------------------------------

 - PRX-CTL-006: the HTTP layer adds no rule. It (a) parses arguments,
   (b) picks the one CLI command line, (c) runs it, (d) classifies the
   outcome for the client using the kernel's own projected availability.
   Classification never decides whether a transition happens.
 - Mutations go only through the CLI child process, which holds the
   `work-protocol` lock and the recovery journals (Program.fs:597-640,
   1275-1360). The web process writes nothing under .ros/.
 - Identity: the child inherits the server process's environment;
   request headers and the peer address are never read for identity.
   An explicit `actor` field is passed as `--actor`, exactly as the
   equivalent CLI command's `--actor` flag (same as the per-action routes).
 - The per-action routes, `/api/v1` read routes and form posts share
   `itemOperation`, `commandLine` and `execute`; none of their behaviour
   changes.

4. Design
---------

Contract: `POST /api/v1/work/:id/transitions`
  Body (JSON or form): `{"action": "ready|block|abandon|start|resume|complete",
  "reason"?, "type"?, "actor"?, "evidence"?: [{type, path}], "conclusion"?}`.

Pipeline (pure where possible):
  1. route: parse body; missing/unknown action -> refusal `invalid-request`
     (400) without touching state.
  2. pre-read: `readStateSources` + `WorkStateView.project`; unreadable ->
     `work-state-unreadable` (500); unknown id -> `work-item-not-found` (404).
  3. operation: `TransitionRequest.operation` picks the CLI command:
     ready -> backlog-transition ready; block -> work block; abandon ->
     backlog-transition abandon (backlog-governed) or work abandon
     (live-governed); start -> work start; resume -> work resume;
     complete -> work complete. Arguments via `itemOperation`.
  4. execute through `CliProcess.runSelf` (the CLI path).
  5. outcome:
     exit 0 -> 200 `{contract: praxis.work-state, version 1, kind:
       "work-transition", action, item: WorkItemState + detail}` read
       in-process after the transition.
     exit 2 -> 400 `invalid-request`.
     other  -> category from the pre-read availability of the requested
       action under the governing kernel:
         not offered / `Refused("illegal-transition")` -> 409 `illegal-transition`
         Legal{Reason=true} and no reason supplied      -> 422 `reason-required`
         Legal{EvidenceTypes<>[]} and refused           -> 422 `evidence-required`
                                                           only if supplied evidence types do not cover them
         otherwise                                      -> 409 `transition-refused`
       Message is always the CLI's own text (`CliProcess.failureMessage`).
     child could not start -> 500 `execution-failed`.
  Refusal body: `praxis.error` v1 `{code: category, error: message,
  message, category, requestedAction, workItemId}` (`error` kept for
  clients of the older shape).

Validation rules: none new; all from the kernel via the CLI.
Error model: the categories above; HTTP 400/404/409/422/500.
Transaction boundary: the CLI command (lock + journal). The pre-read and
the CLI run are not atomic; the category reflects the pre-read state while
the decision and message are the CLI's. A race can only mislabel a category
(e.g. `transition-refused` instead of `illegal-transition`), never apply a
refused transition or change state.

5. Compatibility
----------------

Additive: new route, new `kind` value, new `praxis.error` codes, new
`WorkOperation` case. Existing per-action routes (`/api/work/:id/ACTION`)
and form posts keep working unchanged and are documented as superseded by
the transition endpoint for programmatic clients in docs/web-interface.md.
No .ros/ schema change, no CLI change.

6. Tests
--------

Unit (pure): route of the new endpoint (action + args, missing/unknown
action); operation selection by kernel (abandon live vs backlog, start);
refusal classification table; `commandLine` for `AbandonWork`; refusal and
transition document shapes.
Integration (real `web serve` process, tests/Ros.Tests/WebInterfaceTests.fs):
 - success returns `work-transition` with the resulting typed state for
   ready/start/block/resume/complete/abandon;
 - illegal transition -> 409 `illegal-transition`, requested action, CLI
   message; reason missing -> 422; evidence missing -> 422; unknown item ->
   404; bad action -> 400; each refusal hashes every file of the repository
   (excluding .git) before and after: byte-for-byte equal;
 - identity: server and a CLI run share a declared identity; an API start
   sent with hostile identity-like headers records the same event actor and
   telemetry identity/provenance sources as the CLI start;
 - existing per-action route tests stay green.
Python oracle tests (`python3 -m unittest discover -s tests`) re-run.

7. Risks
--------

 - Refusal paths of the CLI might write (lock file, recovery journal,
   telemetry) before refusing; the byte-for-byte test is the guard. If a
   path writes, the endpoint must not paper over it; report it.
 - Category drift if kernels add rejection kinds; unknown cases fall to
   `transition-refused`, never to success.
 - Pre-read/execute race (section 4); accepted, documented.
 - `work block` on live work may require a durable checkpoint when the
   policy is enabled: surfaces as `transition-refused` with the kernel text.
 - Abandon semantics differ by kernel (reason mandatory for live abandon);
   preserved by delegating to the CLI.
