1. Item and acceptance criteria
-------------------------------

Obligation: `praxis web serve` exposes work state (CTL-02) but nothing about
executions, step receipts, evidence, checkpoints or usage. Those exist only as
CLI output: `execution list|show --json` (src/Ros.Cli/ExecutionCommands.fs:266,
:301), `work context` (src/Ros.Cli/Program.fs:658), `work checkpoint show`
(src/Ros.Cli/CheckpointCommands.fs:524) and `telemetry usage`
(src/Ros.Cli/Program.fs:2564).

Acceptance criteria (numbered as in the description):
 AC1 Typed, versioned read endpoints list executions (optionally for one work
     item) and show one execution: role, status, actor, and
     provider/model/runtime presented as execution-host information, never as
     the owner of work state.
 AC2 An execution's steps with expected and observed receipts and their
     match, mismatch or indeterminate state.
 AC3 A work item's recorded evidence and durable checkpoints.
 AC4 Telemetry usage and cost where recorded, and explicitly unknown
     otherwise.
 AC5 The data is obtained through the same paths as `praxis execution show
     --json`, `work context`, `work checkpoint show` and `telemetry usage`,
     not re-derived.
 AC6 The endpoints never write; tests.

Which "execution": Praxis has two records named execution. (a) The Ordo
execution envelope under .ros/executions/<EXE-ID>/ (envelope.json +
events.jsonl; src/Ros.Infrastructure/Execution/ExecutionStore.fs:18) carries
role, state, actor, provider/model/runtime and the step ledger with expected
and observed receipts. (b) The telemetry execution record under
.ros/telemetry/executions/<EXE-ID>.json carries usage measurements. AC1, AC2
and AC5 ("execution show --json") name (a); AC4 ("telemetry usage") names (b).
The API keeps that split: executions and steps come from (a), usage and cost
from (b), keyed by work item exactly as `telemetry usage ID` keys them.

3. Invariants and shared infrastructure
---------------------------------------

- One path per datum (AC5): every endpoint calls the function the CLI
  command calls (ExecutionSnapshot.load / envelopes, readContextView,
  CheckpointShow read, FileTelemetryUsageRepository.read + Usage.aggregate).
  Moving code to make that possible must leave every CLI output
  byte-identical; existing CLI tests pin that.
- Reads are pure: no lock, no event append, no CLI subprocess. The only
  subprocesses are Git reads the CLI paths already run (diff, ls-files,
  status, rev-parse, ls-remote). `git status` may refresh .git/index as an
  optional lock; those read adapters will run Git with GIT_OPTIONAL_LOCKS=0 so
  a read cannot rewrite the index (same results, no write).
- Host is not owner (PRX-CTL-012): provider/model/runtime appear only under
  `executionHost`, never under `actor`, and the document states that the
  work state is owned by the repository (`workStateOwner: "repository"`,
  plus the work item id).
- Unknown is not zero: an unrecorded host attribute is "unknown"; usage and
  cost metrics nobody recorded are `availability: "unknown"` with no total;
  partial coverage lists the executions that did not report.
- Shared infrastructure touched: ExecutionCommands (load/list moved),
  CheckpointCommands (show read and history node moved), Program.fs
  telemetry usage (group rendering moved), Git read adapters (optional
  locks). All are attributed to this item.

4. Design
---------

Contract A: Ros.Contracts.Execution.ExecutionStateJson,
contract "praxis.execution-state", version 1.

  GET /api/v1/executions[?workItem=ID]
    { contract, version, kind: "execution-list",
      workItem: <qualified id> | null,
      items: [ ExecutionSummary ],
      unreadable: [ { executionId, error } ] }   (envelopes the store holds
                                                  but cannot parse; the CLI
                                                  silently skips them)
  GET /api/v1/executions/EXE-ID
    { contract, version, kind: "execution", execution: ExecutionDetail }

  ExecutionSummary:
    executionId, workItem, role, status, statusReason, startedAt,
    parentExecution, baselineRevision, candidateRevision,
    actor: { id, kind },
    executionHost: { provider, model, runtime  ("unknown" when unrecorded),
                     workspace: {id, mechanism, branch} | null,
                     containment, securitySandbox },
    workStateOwner: { kind: "repository", workItem }
  ExecutionDetail = ExecutionSummary +
    steps: [ { stepId, sequence, name, dependsOn, attempts,
               status (execution show's codes),
               receipt: { state: match|mismatch|indeterminate|not-observed,
                          attempt, expected (ExecutionJson.expected),
                          observed (ExecutionJson.observed) | null,
                          comparison (ExecutionJson.result) | null,
                          observedAt | null, reason | null },
               reconciliation: { finding, detail, at } | null } ],
    scopeEffects (ExecutionJson.scopeEffect), verification | null
  Legal actions for executions are actor-dependent (`execution actions`,
  human-only transitions) and are not part of this read contract.

Domain (pure, Ros.Domain.Execution, new StepReceipts module):
  current attempt = highest Started attempt (0 if none);
  receipt state: never started -> not-observed; started with an Observed
  entry for that attempt -> that comparison's outcome; started without one
  -> indeterminate (effect unknown, the Ordo meaning of a start without a
  receipt). Latest Reconciled entry is reported separately.

Contract B (additive kinds of praxis.work-state v1):
  GET /api/v1/work/ID/evidence[?offline=true]
    { contract, version, kind: "work-evidence", workItemId,
      evidence:    { availability: "available", source: "work context",
                     items: [ {type, path} ], requiredForCompletion: [...] }
                 | { availability: "unavailable", reason },
      checkpoints: { availability: "available", source: "work checkpoint show",
                     remoteObserved, continuity (CheckpointJson.continuity),
                     history: [ CheckpointJson.historyEntry ] }
                 | { availability: "unavailable", reason } }
    A backlog-only item (never started) has no context record: both blocks
    unavailable with that reason. An invalid recorded latestCheckpoint:
    checkpoints unavailable with the problems, evidence still available.
  GET /api/v1/work/ID/telemetry
    { contract, version, kind: "work-telemetry", workItemId,
      executions: [telemetry execution ids in scope],
      usage: [ MetricCoverage for registry sum metrics with unit "tokens" ],
      cost:  [ MetricCoverage for registry sum metrics with unit "currency" ],
      groups: [ TelemetryUsageJson.group ]   (exactly `telemetry usage ID
                                              --by execution` groups) }
    MetricCoverage: { metric, unit,
                      availability: "recorded" | "partial" | "unknown",
                      totals: [ {currency, total} ],
                      reportingExecutions, unavailableExecutions }
  Domain (pure, Usage.coverage): from registry metrics, the executions in
  scope and the work-item-dimension groups of Usage.aggregate; no new
  summing.

Error model (praxis.error v1, as CTL-02): unknown work item -> 404
work-item-not-found; unknown execution -> 404 execution-not-found;
unparseable envelope or unreadable state -> 500 execution-unreadable /
work-state-unreadable.

Stores: none new; no writes. Transaction boundaries: none (reads only, no
lock taken).

Routes: GET /api/v1/executions, /api/v1/executions/ID,
/api/v1/work/ID/evidence, /api/v1/work/ID/telemetry. Other methods on these
paths fall through to the existing /api 404 JSON.

5. Compatibility
----------------

- Additive routes under /api/v1/; CTL-02 routes and legacy /api/work unchanged.
- `execution show|list --json`, `work checkpoint show [--json]`,
  `telemetry usage --json`, `work context` outputs unchanged (moved code, not
  changed code); existing tests for each stay green.
- GIT_OPTIONAL_LOCKS=0 on read adapters: Git returns the same answers; only
  the opportunistic index refresh is skipped.
- docs/web-interface.md gains the new routes and the two contracts.

6. Tests
--------

- Pure: StepReceipts state for not-started, started-unobserved,
  observed match/mismatch/indeterminate, retry after mismatch; Usage.coverage
  recorded / partial / unknown / no executions, currencies kept apart.
- Contract: execution document puts provider/model/runtime under
  executionHost only, "unknown" for unrecorded, workStateOwner present;
  receipts reuse ExecutionJson shapes; coverage unknown has no total.
- Routing: the four routes map to the new route cases.
- HTTP (real server, temp repository): execution started via the CLI, a
  step declared and run (match) and one run to mismatch -> list (all and
  filtered by work item), show with receipts; parity with `execution show
  --json` for shared fields; evidence and checkpoints for a started item with
  a checkpoint pushed to a bare remote, parity with `work checkpoint show
  --json`; telemetry with a recorded tokens metric (recorded) and cost not
  recorded (unknown), parity with `telemetry usage --json`; unknown work item
  and execution -> structured 404; every repository file (including .git)
  byte-identical before and after all GETs (AC6).

7. Risks
--------

- Moving CLI code could alter CLI output: mitigated by keeping renderers
  identical and running the full suite (CLI tests pin these outputs).
- Remote observation on each evidence request costs an ls-remote (bounded by
  ROS_GIT_REMOTE_TIMEOUT_SECONDS); `?offline=true` avoids it, and the
  document says whether the remote was observed.
- In this repository no Ordo execution envelopes exist yet (.ros/executions
  absent), so the execution endpoints are exercised by tests, not by live
  data; the list answers an empty, truthful list.
- Two "execution" records with the same id format (EXE-...) may confuse
  clients; documented: /api/v1/executions are Ordo envelopes, telemetry
  executions appear in work-telemetry.
- `scopeEffects` and the uncommitted flag depend on the server's working
  tree at read time, exactly as `execution show` does.
