5. Build/test procedure
-----------------------
The requested local procedure was to use clean arm worktrees/clones and run:

  dotnet build Ros.slnx -c Release \
    -p:FSharpCoreImplicitPackageVersion=10.1.400

followed by the F# test assembly, supported Node differential tests and Python
tests, plus symmetric independent CLI fixtures.

That exact local procedure could not be executed because the available local
container had no .NET SDK and could not resolve github.com to fetch exact-SHA
worktrees.

To avoid weakening the blind or fabricating results, I used existing GitHub
Actions runs attached directly to the permitted exact arm SHAs. Both runs were
push-triggered on the permitted blind branches. Both installed .NET 10.0.x
(SDK 10.0.401) and ran the repository's validation job, including
npm run test:all and ./ros validate.

The CI build command visible in the logs was:

  dotnet build Ros.slnx --configuration Release --disable-build-servers
    --maxcpucount:1 -p:UseSharedCompilation=false -p:BuildInParallel=false

It did NOT include the requested
-p:FSharpCoreImplicitPackageVersion=10.1.400 override. Consequently, the exact
requested build invocation is not independently confirmed by this evaluator.

The repository CI also ran packaged-lifecycle jobs on Ubuntu 24, Ubuntu 20,
macOS 22 and Windows 22; all succeeded for both exact arm SHAs.

Independent acceptance-probe limitation:
I could not run a new, evaluator-authored fixture matrix or a multi-process
concurrency stress probe. Existing arm tests do run real CLI fixtures in
temporary repositories/clones and cover most requested scenarios, but those
tests are implementation-supplied rather than an independently authored
symmetric probe suite. Findings that depend specifically on concurrent runtime
interleavings are therefore classified as design risks rather than asserted as
observed runtime failures.

7. Acceptance-criteria matrix
-----------------------------
Legend:
  confirmed      evidence supports the criterion
  partial        core behavior works but a stated requirement/probe is missing
  defect         concrete behavior contradicts a requirement
  design-risk    plausible architectural failure mode not runtime-observed here
  not-confirmed  insufficient evidence

PRAXIS-GROUP-01 CREATE
Arm M: PARTIAL / DEFECT
- Confirmed: valid creation, duplicate-ID refusal, duplicate-member refusal,
  unknown/terminal refusal, --dry-run, --json, lifecycle non-mutation, planner
  consumption, stored-state validation.
- Defect M-D1: a created group can persist no execution repository at all.
- Defect M-D2: create does not apply the repository-compatibility admission
  rule that add applies, so a non-cross-repository group can be initially
  created with a foreign-repository member.
Arm N: CONFIRMED
- Valid creation, unknown/terminal/duplicate rejection, repository compatibility,
  local-repository default, cross-repository admission, dry-run, JSON,
  lifecycle non-mutation, planner projection and validation are all directly
  implemented and exercised.

PRAXIS-GROUP-02 SHOW
Arm M: CONFIRMED
- Text/JSON, unknown exit 1, recorded/planning state, partial progress, blocked
  members and gates, execution repository and architecture notes are covered.
- A repository fingerprint test confirms read-only behavior.
Arm N: CONFIRMED
- Text/JSON, unknown exit 1, recorded/planning state, progress, blocked/gates,
  execution repository, architecture notes and read-only behavior are covered.

PRAXIS-GROUP-03 ADD
Arm M: CONFIRMED, with concurrency design risk
- Unknown/terminal/already-present refusal, repository mismatch unless
  cross-repository, provenance, dry-run/JSON, and lifecycle non-mutation are
  implemented and tested.
Arm N: CONFIRMED
- The same central admission function used by create is reused by add.
- Refusals, cross-repository behavior, structured actor provenance, dry-run,

PRAXIS-GROUP-04 REMOVE
Arm M: CONFIRMED, with concurrency design risk
- Non-member refusal, provenance, lifecycle/evidence/attribution preservation
  and explicit minimum-size behavior are tested.
- M is stricter than the minimum acceptance rule: it refuses a removal that
  would leave fewer than two members.
Arm N: CONFIRMED
- Non-member and last-member refusal, provenance, dry-run and preservation of
  completed member lifecycle/evidence/attribution are tested.

PRAXIS-GROUP-05 CHECKPOINT
Arm M: CONFIRMED
- Reuses work-checkpoint durability verification; uncommitted/unpushed work is
  refused with the same durability codes.
- Requires an active member and this executor's own active execution.
- References members' own checkpoints; keeps uncheckpointed members explicit.
- Preserves active/completed/abandoned/remaining distinctions.
- Rejects blank summary, blank next action and blank shared decisions.
- Validation detects a member reference to another member's checkpoint.
- Group checkpoint write is under work-protocol lock.
Arm N: PARTIAL / DEFECT
- Core durable Git verification, member checkpoint references, branch/commit,
  next action, shared decisions, no claimed paths, uncommitted/unpushed refusal
  and member-history preservation are confirmed.
- Defect N-D1: blank shared decisions are silently trimmed/filter-dropped rather
  than refused.
- Defect N-D2: stored checkpoint validation does not verify that a referenced
  checkpoint belongs to the named member, so a constructed attribution-
  laundering representation is not detectable by validate.
- Design risk N-R2: an abandoned member can fall outside all three serialized
  active/completed/remaining lists because planner status classifies abandoned
  as complete while CompletedMembers checks recordedState == "complete".
  The baseline does not state an explicit abandoned serialization rule, so
  this is not counted as a confirmed acceptance defect.

M-F09
FACT
Arm: M
Cross-item concern: concurrency/locking.
Observed: create/add/remove perform read-decide-write using FileWorkGroupStore
and an atomic temp-file replacement, but no lock spans the read-modify-write
cycle. The checkpoint CLI separately acquires the existing work-protocol lock.
Expected: simultaneous successful group mutations should not overwrite each
other, and lifecycle transitions should not race admission decisions.
Evidence:
- src/Ros.Infrastructure/Planning/FileWorkGroupRepository.fs:31-43, 66-80
- src/Ros.Cli/WorkGroupCommands.fs:393-450
INFERENCE
Two create/add/remove processes can read the same old groups.json and each
atomically replace it with a different successor, causing a lost update even
though both processes can exit successfully. Group mutation can also interleave
with checkpoint despite checkpoint taking a lock, because the group mutation
does not participate in that lock.
DESIGN JUDGMENT
Atomic replacement prevents torn files but is not an atomic read-modify-write
transaction.
Result: design-risk
Identifier: M-R1
Runtime concurrency probe: not-confirmed due evaluator environment limitation.

M-F10

checkpoints live in .ros/work/group-checkpoints.json. The declaration model
reuses the planner's DeclaredGroup, while checkpoint is a separate typed model.

but a sixth command spanning both concerns would need orchestration across more

DESIGN JUDGMENT

important than the number of files.
Result: partial / design-risk

10. Cross-item architecture comparison
--------------------------------------
GROUP MODELS
Arm M:
- persistent StoredGroup wrapping the existing planner DeclaredGroup;
- existing planner WorkGroup as analyzed runtime view;
- separate GroupCheckpoint model and progress/reference records.
The main declaration model is reused rather than copied, but checkpoint state
is deliberately separate.

Arm N:
- persistent StoredGroup with membership history and checkpoint history;
- request/view records around it;
- existing planner DeclaredGroup/WorkGroup reached through projection.
The persistent concept is more centralized; request/view models are normal
boundary representations, not competing persistence models.

PERSISTENCE STORES
Arm M: two group-related files:
  .ros/work/groups.json
  .ros/work/group-checkpoints.json
Arm N: one:
  .ros/work/groups.json
with checkpoints embedded per group.

MEMBER-ADMISSION RULES
Arm M: create and add have separate admission logic. This causes the concrete
repository-invariant drift in M-D2.
Arm N: one WorkGroups.admit rule reused by create and add.

GROUP-ID GRAMMARS
Arm M: one new regex requiring GROUP- plus at least two hyphen-separated
segments after GROUP.
Arm N: one new regex allowing GROUP- plus one or more segments.
Baseline PRX-GRP-010 gives a suggested grammar and explicitly permits existing
Praxis identity conventions, so the difference is indeterminate rather than a
proven defect.

MEMBER STATE / PROGRESS CLASSIFICATION
Arm M:
- membership admission uses effective lifecycle strings;
- show uses the existing planner classification;
- checkpoint has an explicit active/completed/abandoned/remaining partition.
Arm N:
- GroupMemberFacts centralizes recorded state;
- show uses planner status;
- checkpoint reuses show but recomputes active/completed/remaining from a mix
  of planner status and recorded state, producing N-R2 for abandoned members.

JSON ENVELOPES
Arm M:
- one work-groups persistence schema for create/add/remove;
- a distinct work-group-checkpoints schema;
- show uses the existing planner declared-group schema;
- mutation commands have command-specific result shapes/kinds.
Arm N:
- one WorkGroupJson persistence codec and one common command envelope
  (command/schemaVersion/groupId/status), with verb-specific payload fields.
Arm N is more uniform at the CLI JSON boundary.

CLI PARSING / MUTATION PIPELINES
Arm M:
- create/add/remove share local parser helpers but call separate application
  operations; show lives in PlanCommands; checkpoint has its own lock wrapper
  and repository.
Arm N:
- create is one path;
- add/remove explicitly share membershipChange;
- show and checkpoint remain separate where semantics differ;
- all group writes funnel through one locked repository mutation function.
Arm N has fewer independent mutation pipelines.

CHECKPOINT REPRESENTATIONS
Arm M: group checkpoint is separate from declaration state and has explicit
abandoned/uncheckpointed/execution-reference fields plus GitDurableLocation.
Arm N: group checkpoint is embedded in StoredGroup and content-addressed. It
has active/completed/remaining and optional member checkpoint fields, but no
separate abandoned category.

RULE REUSE VS COPYING
Arm M reuses planner DeclaredGroup and work-checkpoint durability but duplicates
member-admission logic between create and add.
Arm N reuses WorkGroups.admit, group history, view, one JSON codec and one
transaction path. Its main validation gap is not duplication but missing
cross-record ownership validation.

CREATE/ADD/REMOVE INVARIANTS
Arm N is internally more consistent because create and add share admission.
Arm M disagrees with itself on repository admission: add enforces it, create
does not.
Both preserve member lifecycle/evidence/attribution on membership mutation.

SHOW/CHECKPOINT CLASSIFICATION
Arm M show uses planner status while checkpoint independently partitions
effective lifecycle and explicitly preserves abandoned.
Arm N checkpoint reuses the show view but mixes view.Status and RecordedState,
which is mostly cohesive but creates the abandoned-classification risk.

PLANNER / MUTATION AGREEMENT
Both project persisted groups into the planner.
Arm M refuses a stored/configured duplicate ID as ambiguous.
Arm N gives explicit per-run configuration precedence over stored state.
The acceptance criteria do not specify duplicate-source precedence; neither
choice is scored as a defect.

EXISTING PARSER/RULE REUSE
Both reuse existing PlanningJson/planner/work-checkpoint machinery.
M reuses the existing planner DeclaredGroup directly.
N adds a focused WorkGroupJson codec but reuses planner Grouping and existing
checkpoint verification.

DEPENDENCIES
Neither arm introduces a new external package dependency in the patch.

LOCKING / ATOMICITY / LOST UPDATE
Arm N: lock + atomic write around all group mutations.
Arm M: atomic file replacement but no lock around declaration/member
read-modify-write. Lost-update risk remains and checkpoint's lock does not
serialize against those unlocked mutations.

STALE / ORPHANED RECORDS
Arm M's second checkpoint file increases cross-file referential surface, but
validation checks checkpoint group IDs and member checkpoint ownership.
Arm N keeps checkpoint history embedded, eliminating cross-file group/checkpoint
orphaning but misses external member-checkpoint ownership validation.

ERROR HANDLING
Both consistently distinguish argument/usage errors from semantic refusals in
tested paths. Arm N has a single machine-readable rejection-code family.
Arm M show uses planner error output while mutation commands use work-group
renderers, so its JSON/error surface is less uniform.

MAINTAINABILITY FOR COMMAND SIX/SEVEN
Arm M has clearer layer separation but more plumbing and two persistence
surfaces. A cross-cutting command can require updates in domain, application,
contract, infrastructure and possibly PlanCommands.
Arm N has a simpler vertical path and shared transaction/envelope behavior,
but WorkGroups.fs is already broad and should be split by pure subdomain if
future command count grows.

MONOLITH VS OVER-FRAGMENTATION
Arm M: no individual module is monolithic; the risk is over-fragmentation at
the CLI/store boundary, especially show living in PlanCommands and checkpoint
living in a separate store while other mutations do not share checkpoint's
lock.
Arm N: WorkGroups.fs is large, but current internal concepts are coherent and
shared; it is a maintainability risk rather than a demonstrated monolith
defect.

11. Test-quality comparison
---------------------------
Both arms use meaningful tests rather than only implementation mirrors:
- pure decision tests;
- JSON round trips;
- actual CLI execution;
- temporary repository/clone fixtures;
- Git durability scenarios;
- lifecycle/evidence preservation checks;
- planner integration and validation.

Arm M's test suite is broader around checkpoint integrity:
- explicit blank shared-decision rejection;
- sequential checkpoint IDs;
- executor-ownership checks;
- cross-member checkpoint laundering validation;
- bad/backdated timestamps;
- checkpoint dry-run;
- separate validation of group-checkpoint storage.
This breadth is directly useful because it catches a class of error Arm N's
suite does not test.

Arm N's test suite is stronger around one end-to-end group surface:
- structured Actor provenance in append-only history;
- architecture-note create/show round trip;
- one shared create/add repository-admission rule;
- single-store show/checkpoint integration;
- completed-member removal preserving lifecycle/evidence/attribution.

Meaningful gaps:
- Neither arm contains a multi-process lost-update/concurrency stress test.
- Arm M lacks a create-time foreign-repository test, allowing M-D2 through.
- Arm N lacks a blank-shared-decision test and a validator test for a member
  referencing another member's checkpoint, allowing N-D1/N-D2 through.
- Neither test count is treated as evidence by itself.

13. Design risks
----------------
ARM M
M-R1: unlocked read-modify-write on groups.json can lose concurrent successful
create/add/remove mutations and can race a group checkpoint/lifecycle
transition. Atomic replacement protects file integrity, not transaction
integrity. Runtime reproduction was not possible in this evaluator environment.

M-R2: two persistence stores and multiple JSON/schema families increase
cross-command integration surface. This separation also has benefits, so it is
not itself a defect.

ARM N
N-R1: WorkGroups.fs is a broad domain module. Current reuse is coherent, but
continued command growth could turn it into a monolith unless split by pure
concern.

N-R2: abandoned member state can disappear from all serialized
active/completed/remaining checkpoint lists. The baseline does not prescribe an
abandoned field, so this remains a design risk rather than a confirmed defect.

14. Areas where M is stronger
-----------------------------
- Checkpoint integrity and validation are more explicit.
- Validation can detect cross-member checkpoint-reference laundering.
- Group checkpoint progress preserves abandoned separately instead of silently
  folding or dropping it.
- Checkpointing requires the evaluator/executor to own an active execution of
  an active member, an additional attribution safeguard.
- Blank shared decisions are explicitly rejected.
- Group checkpoint supports dry-run even though the minimum acceptance text
  does not require it.
- Test coverage is materially deeper around checkpoint corruption and
  attribution boundaries.
- Domain/application/infrastructure separation is clearer for pure decisions
  and ports.

15. Areas where N is stronger
-----------------------------
- One reusable member-admission rule keeps create/add repository invariants
  aligned.
- Every group has an execution repository; create defaults to the local
  repository.
- One work-protocol lock protects every group read-modify-write transaction.
- One group store avoids declaration/checkpoint cross-file update surface.
- One JSON codec and common command envelope make JSON behavior more uniform.
- Structured Actor provenance retains more identity structure than a bare
  actor ID string.
- Architecture notes are accepted at create and shown through the same stored
  model.
- add/remove share one mutation pipeline, reducing parser/behavior drift.

16. Areas equivalent/indeterminate
----------------------------------
Equivalent or effectively equivalent:
- basic valid create;
- unknown/terminal/duplicate create refusals;
- duplicate member handling;
- lifecycle non-mutation;
- create/add/remove JSON and dry-run where required;
- add already-present refusal;
- remove non-member/last-member explicit behavior;
- text/JSON show and unknown exit 1;
- planner visibility of stored declarations;
- work-checkpoint Git durability reuse;
- branch/commit/next-action/shared-decision persistence;
- member checkpoint history is referenced rather than replaced;
- no new external dependencies;
- successful exact-SHA CI validation.

Indeterminate by authoritative criteria:
- M's stricter minimum of two group members versus N allowing a one-member
  group. The baseline describes groups as several items but does not state a
  normative minimum cardinality in the cited requirements.
- M refusing a stored/configured duplicate group ID versus N allowing explicit
  config to shadow stored state. Precedence is not specified.
- M's stricter group-ID regex versus N's broader regex. PRX-GRP-010 says the
  exact form may follow existing conventions.
- Relative performance/cost/speed. Those metrics were deliberately excluded
  from this blind implementation-quality evaluation.

17. Threats to validity
-----------------------
1. The evaluator could not run the required exact local build command because
   .NET was unavailable locally. The exact-SHA CI build used .NET 10.0.401 but
   did not pass FSharpCoreImplicitPackageVersion=10.1.400.
2. The evaluator could not create clean local worktrees because the local
   container could not resolve github.com.
3. A fresh evaluator-authored symmetric CLI probe matrix was not executable.
   Existing exact-SHA CLI tests are substantial but were authored by each arm.
4. Concurrency behavior was inspected statically. Arm M's lost-update mechanism
   is technically clear, but no simultaneous-mutation runtime reproduction was
   performed, so it is a design risk rather than an observed defect.
5. Source-code comments and organization can reveal implementation style.
   They did not reveal execution-mode mapping.
6. CI success demonstrates the committed arm tree passed its repository suite;
   it does not prove every acceptance criterion, which is why static semantic
   review and gap analysis were also performed.

19. Final qualitative synthesis
-------------------------------
Both arms implement the five-command work-group surface substantially and both
pass the permitted exact-SHA repository CI. Their core create/show/add/remove
and durable-checkpoint paths are not superficial: each has real CLI fixtures,
planner integration, JSON contracts and non-mutation checks.

Arm M is stronger on checkpoint integrity. Its group-checkpoint model makes
member checkpoint ownership, abandoned members, executor ownership and
durability explicit, and its validator directly detects attribution
laundering. Its main weakness is earlier in the lifecycle: create does not
establish the execution-repository invariant that add establishes, and its
unlocked group read-modify-write path creates a credible concurrency/lost-
update risk.

Arm N is stronger on cross-command cohesion. One admission rule, one locked
mutation path, one group store and one command envelope reduce drift, and that
cohesion is visible in correct repository enforcement at both create and add.
Its main weakness is checkpoint validation depth: blank shared decisions are
silently discarded, and validate cannot prove that persisted member checkpoint
references actually belong to the named members.

The evidence therefore supports specific, localized comparative statements:
Arm M has the more defensive checkpoint integrity model; Arm N has the more
consistent repository-admission and transactional mutation model. Both have
confirmed acceptance defects, and the available blind evidence does not justify
a numeric score, an overall winner, a methodology conclusion, or any inference
about which execution mode produced either implementation.
