information about the other. The orchestrator did not check the arms'
session event logs for compliance, so that check remains open for the
evaluator (as in the A021 protocol).

8. Protocol deviations
----------------------
Both arms, and the environment:
  E1. No .NET was preinstalled. The Microsoft download hosts and
      scripts/install-toolchain.sh's release lookup returned HTTP 403. Both
      arms installed dotnet-sdk-10.0 10.0.112 from the Ubuntu archive. Its
      FSharp.Core is older than the repository requires, so every build used
      -p:FSharpCoreImplicitPackageVersion=10.1.400 (and the npm scripts were
      run as their constituent steps). No repository file was changed for
      this. The same workaround was used in both arms.
  E2. The orchestrator added the same neutral note to both prompts: install
      .NET with the repository's own scripts if it is missing, and use the
      baseline's session_metrics.py for metrics if helpful. Neither note
      appeared in the original A021 frozen prompts.
  E3. Sessions created with create_session carry the reserved tag
      config:auto-create-pr:draft, which cannot be removed. No PR was
      actually opened for either arm branch.

Grouped arm:
  G1. The group analysis was committed as group-analysis.txt, not
      group-analysis.md, because `./ros validate` rejected the .md (the
      experiment-record rule above). The content was moved unchanged.
  G2. grouped.json was captured before PRAXIS-GROUP-05's checkpoint and
      completion, so the last few minutes and 2 commits are not counted in
      it. commitsAtSnapshot is 11; the final branch has 13 commits. Cost is
      recorded there as unknown; the platform cost is in section 4.

Control arm:
  C1. Toolchain: as E1.
  C2. Workers started from a stale checkout. Although each worker was
      created after the previous worker's commits were on the remote, the
      first commits of C2 (962b1f4) and C3 (b05fd8b) are parented on the
      baseline 8b4ffa3, not the branch head. The most likely cause is that
      the platform served a checkout that did not yet include the latest
      push. This is not confirmed.
        - C2 implemented `work group show` (962b1f4) without GROUP-01's code
          in its workspace. It then merged GROUP-01 from the remote (fa821cc),
          resolving conflicts, renaming one clashing function and adding a
          test. So GROUP-02 was initially designed without the repository
          state the protocol intended it to see.
        - C3 recorded its work start on the stale base, then merged
          GROUP-01/02 (5a03452) before writing any implementation. The effect
          on its design is expected to be small, but it is recorded.
        - C4 and C5 started from the current head.
      No one repaired this. The control branch therefore has two merge
      commits.
  C3. Worker metrics were captured before each worker's final
      completion/commit steps. Whole-session platform usage is in section 4.
  C4. The metrics schemas differ between workers, because each worker wrote
      its own file. control-01.json has no failedTests, retries,
      validationFailures or commits fields. control-04.json and
      control-05.json have no contextResets field. The missing values are
      unrecorded, not zero, and no one filled them in afterwards.
  C5. The control run log is a .md file under research/experiments
      (control-run-log.md). Agent C reports that `./ros validate` passed at
      0b9e81f, before the log was committed. The final tip 8bb8f78 was not
      re-validated by the orchestrator, and by the rule in G1 it may fail
      validation.
  C6. No replacement workers were needed. Every worker completed its item
      in its first session.

Orchestrator:
  O1. The orchestration branch's own commits (this record and the blind kit)
      were made without a Praxis work item or `./ros` lifecycle, because
      there is no local .NET runtime in the orchestrator container. No Praxis
      state was hand-edited.
  O2. The original A021 prompts named the branch without a replication
      suffix. The R2 prompts carry the fuller R2 instructions given by the
      repository owner (the group-analysis sections, per-milestone
      checkpoint content, and metrics fields). Both arms received their
      instructions in the same form.


9. Validity for evaluation
--------------------------
Grouped arm: valid for evaluation. All five items are complete under
separate lifecycles, the analysis was committed before code, and the
deviations (G1, G2, E1) are recorded and do not affect the independent
variable.

Control arm: valid for evaluation, with deviation C2 flagged. The independent
variable was respected: five fresh, isolated contexts ran strictly in order,
and no shared-context substitution was made. However, C2 (and nominally C3)
began from the baseline instead of the branch head. That departs from the
protocol's "later workers see earlier workers' pushed commits", and it makes
GROUP-02 somewhat more independent than designed. The evaluator and the
metrics comparison should take C2 into account, for example as a threat to
validity on cross-item consistency and merge churn. Whether to accept the
arm as is or re-run GROUP-02 is the repository owner's decision.
