# Public site architecture

The public Praxis website lives in [`site/`](../site/). It is a separate
boundary from the operational web UI in [`web/`](../web/), and the two must not
be merged. Work item: `PRAXIS-SITE-01` (GH-84).

| | `web/` (and `web-hub/`) | `site/` |
|---|---|---|
| Purpose | Operational work-backlog UI for one repository (or the project-administration hub) | Public explanation of Praxis |
| Audience | The repository's own operators | Anyone on the internet |
| Served by | `tools/ros_server.mjs` / `tools/ros_hub_server.mjs`, a privileged localhost HTTP adapter over repository state | Any static host (GitHub Pages) |
| Backend | Yes: reads and mutates `.ros/` state through the Praxis HTTP adapter | None: static files only |
| Data | Live repository state | A committed, reviewed, public-safe snapshot (`site/data/`) |
| Build | `npm run build:web` (TypeScript) | None: plain HTML, CSS, and a small script |

## Rules

- `site/` never calls the operational HTTP interface. It contains no
  `localhost`, loopback, or adapter API references. CI enforces this
  (`site-tools/check.mjs`).
- Everything in `site/` is public. Nothing private is copied into it by hand.
  Evidence shown on the site is generated by `site-tools/evidence.mjs` from
  committed Praxis records, and it keeps only a reviewed, public-safe subset.
  See [Public and private evidence](#public-and-private-evidence).
- All asset references are relative, so the site works at a domain root and at
  a GitHub Pages project path (`https://<owner>.github.io/praxis/`).
- The site works without JavaScript and without web fonts. Script only
  enhances; it never carries content.
- No framework, bundler, runtime backend, database, or analytics. No package
  dependencies are added for the site.
- `site/` is not part of the npm package (`package.json` `files`) and is not
  embedded in the CLI scaffold.
- The site tooling lives in `site-tools/`, not `scripts/`, and adds nothing to
  `package.json`. `native-release.yml` rebuilds and re-uploads release assets
  on pushes to `main` that touch `scripts/**` or `package.json`, so a site
  change must never touch those paths. `tests/site/workflow.test.mjs` enforces
  this.

## Local preview

```bash
node site-tools/serve.mjs            # http://127.0.0.1:4173/
node site-tools/serve.mjs --port 8080
```

The preview server serves only `site/`, binds to loopback, and refuses path
traversal. It is a development convenience. It is not the deployment
mechanism.

## Checks

```bash
node site-tools/verify.mjs             # all of the below, in order; what CI runs
node site-tools/evidence.mjs           # regenerate site/data/gh-84.json from .ros records
node site-tools/evidence.mjs --render  # rewrite the ledger and every data-evidence value in the page
node site-tools/evidence.mjs --check   # the snapshot matches the records, the page matches the snapshot
node site-tools/check.mjs              # structure, references, accessibility rules, boundary
node --test tests/site/*.test.mjs      # the same rules as tests, plus contrast
```

## Public and private evidence

The site deliberately shows real Praxis evidence about its own construction
(GH-84). The generator publishes only these fields:

- work-item IDs, titles, and lifecycle states;
- execution IDs, status, and start and finalization times;
- the recorded actor kind, provider, runtime, and model (as recorded,
  including `unknown`);
- the parent-execution link;
- the repository branch and short commit at the start and end of an execution;
- derived execution measurements: wall time, commits created, files added and
  modified, tests added;
- completion evidence paths (repository-relative) and the work item's source
  reference;
- whether each telemetry metric is recorded, unavailable, or unknown, but not
  the raw provider payloads.

It never publishes:

- session, conversation, or run IDs;
- local paths or environment values;
- raw telemetry payloads or credentials.

The generator strips these fields, and the site check fails when the snapshot
contains anything that looks like a session identifier, a local path, or a
credential.

## Deployment

`.github/workflows/site-pages.yml` checks the site, assembles `site/` as the
Pages artifact, and deploys it with GitHub's Pages actions. It is independent
of the npm and native release workflows. See
[`site-deployment.md`](site/site-deployment.md) for the one-time repository
setting that a maintainer must make.
