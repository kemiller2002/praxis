## Finding

When Causa Rehearsal 3 derived its requirements from the authoritative
project (kemiller2002/Indy-init), the mandatory P0 requirement "UI-016: Causa
semantic color system" disappeared. Its obligations were an exact palette
(`#14283F`, `#087F8C`, `#E9A23B`, `#D66B58`, `#F5F3ED`) mapped to Forma
tokens, WCAG AA contrast, color never the sole indicator, legible grayscale
print, screenshots from the deployed exact SHA at desktop, iPad
portrait/landscape and mobile sizes, and independent visual review; "A
grayscale-only interface is a failed UI-016 acceptance even if functional
tests pass". Nothing detected the loss: the closest derived criterion
(RQ-CAUSA-2026-0008 UI-03, "Status is never conveyed by colour alone") is a
generic accessibility criterion that carries none of the palette or visual
acceptance obligations.

## Requirement

Praxis provides a reusable, deterministic requirements-preservation gate
(`praxis requirements preservation verify`). No LLM is used.

1. An authoritative baseline manifest records the source repository, the
   pinned commit SHA, the source documents with the SHA-256 of their text, and
   an inventory of source requirements. Each requirement has a stable id, a
   priority and a list of structured mandatory obligations; each obligation
   has an id, verbatim source text and a kind (`value`: exact tokens such as
   hex values that must appear; `acceptance`: a verification obligation such
   as deployed screenshots; `constraint`).
2. A derived-package disposition file gives each source requirement a
   disposition (Preserved, Strengthened, ExcludedWithApproval referencing an
   approval record with decision id, approving authority, scope and date,
   Superseded by an approved replacement, NotApplicable with a
   justification) and maps every source obligation to the derived
   requirement criterion that carries it.
3. Deterministic checks:
   - a missing disposition for an applicable mandatory requirement fails;
   - a disposition that drops an obligation (not mapped to any derived
     criterion) fails;
   - the exact tokens of a `value` obligation must literally appear in the
     mapped derived criterion text;
   - an `acceptance` obligation must map to a derived acceptance criterion;
   - an exclusion without a valid approval record fails, and approval
     records are never generated by the gate;
   - a source text hash that differs from the pinned inventory is drift that
     fails until reconciled;
   - declared conflicting mandatory requirements are BLOCKED pending a
     decision;
   - one source requirement may map to many derived criteria only when every
     obligation is covered;
   - mapping to a derived criterion that does not contain the value
     obligations (false equivalence) fails, and where only semantic judgement
     could decide, the gate emits a reviewable NeedsReview finding that blocks
     acceptance; it never silently accepts.
4. Output is machine-readable JSON under a versioned Praxis schema plus a
   human summary; the exit code is nonzero on FAIL or BLOCKED.
5. Regression tests A-L with fixtures:
   A complete preservation passes; B UI-016 removed fails; C palette replaced
   with "use appropriate colors" fails; D palette kept but the
   deployed-screenshot obligation removed fails; E an approved exclusion
   passes and is visible in the report; F an unapproved exclusion fails; G a
   changed source baseline is detected as drift; H conflicting requirements
   are BLOCKED; I one-to-many mapping passes only when all obligations are
   covered; J a visual-identity requirement mapped to a generic accessibility
   criterion fails or is BLOCKED; K a read-only scope's approved exclusion of
   write workflows, with UI, security and accessibility preserved, passes; L
   Rehearsal 3 regression: a fixture reproducing the original R3 package
   (UI-016 absent), built from the real files with their source SHAs
   recorded, is detected, and a corrected package passes.
6. Documentation: a requirements-preservation contract (data model,
   dispositions, approval records, drift, exit codes, ownership boundary:
   Praxis owns intake, provenance, derivation and disposition; Ordo owns
   decision authority for approvals; Dokimos owns verification gates;
   Percepta owns semantic UI verification) and how a future rehearsal
   initialisation uses the gate (resolve the authoritative commit, inventory,
   scope, approved exclusions, derive, reconcile, run the gate, record the
   baseline, begin implementation only after PASS).

## Acceptance criteria

- `praxis requirements preservation verify` exists with the behaviour above
  and is implemented in F# under the four-tier architecture.
- Versioned JSON schemas for the baseline, disposition, approvals and report
  documents exist under `schemas/`.
- Tests A-L exist as Praxis tests with fixtures and pass; the full build and
  test suite pass.
- The contract document exists and is linked from the CLI reference.
