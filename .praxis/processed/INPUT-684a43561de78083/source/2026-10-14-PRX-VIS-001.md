## Original requirements and acceptance criteria from GitHub issue #270

## Problem
Work can pass compilation, product-state tests and foundation-adoption checks while shipping unsupported CSS tokens or visually inconsistent colors. A worker's assertion that visual review was done is insufficient without independent, reproducible evidence.

## Requirements
- **PRX-VIS-001.1:** On UI-bearing work packages, receive an immutable visual decision/requirement manifest from Ordo ([#92](https://github.com/kemiller2002/ordo/issues/92)) and preserve a source commit, package versions and approved decision ID.
- **PRX-VIS-001.2:** Before accepting, integrating, or completing the package, require independent Dokimos token-contract evidence ([Dokimos #41](https://github.com/kemiller2002/dokimos/issues/41)) and Visual Engineering rendered-evidence manifest ([VE #49](https://github.com/kemiller2002/visual-engineering/issues/49)). Check artifact identity, expected states/viewports/themes and actual test results, not just receipt presence.
- **PRX-VIS-001.3:** Reject absent/stale mismatched receipts, invalid tokens, missing required screenshots, unapproved palette changes, and critical contrast/state violations. Support explicit NOT_APPLICABLE, UNKNOWN and governed exceptions; UNKNOWN is never auto-PASS.
- **PRX-VIS-001.4:** Allow normal intermediate compilation/testing for diagnostics. Gate *acceptance and integration*, not every edit/compile. Batch visual checks at coherent work-package boundaries to avoid repeated full CI and GitHub wait.
- **PRX-VIS-001.5:** Keep local-first, OS/worker neutral verification with replaceable browser/adapters; do not mandate Kubernetes or external orchestration services. Reuse existing signed-receipt and checklist infrastructure when appropriate rather than duplicating policy logic.
- **PRX-VIS-001.6:** Make the output a versioned evidence record referencing original requirement IDs, approved visual decisions, inspected commit, and failures/unknowns so cohort jobs can hand off without natural-language drift.

## Acceptance criteria
- A signed/valid but stale or wrong-commit visual receipt is refused.
- An application that compiles with Summa's unknown color references is refused for completion; correcting the tokens enables acceptance when all other checks pass.
- A high-contrast but inappropriate product palette is not automatically approved solely on computed contrast.
- Runs complete locally on supported platforms using available browser facilities; untested platforms are UNKNOWN.
- Execution-time comparison demonstrates acceptable overhead and supports bounded, end-biased CI batching.
