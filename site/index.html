Praxis

You said it’s done. Prove it.

Praxis connects requirements, execution, agents, changes, tests, evidence, provenance, and cost into a verifiable engineering record.

Trust is not an engineering control. Evidence is.

See the evidence View on GitHub

The problem

An agent says the work is done. Now answer the questions.

  1. Which requirement was this for?
  2. Who, or what, did the work?
  3. Which provider, runtime and model?
  4. What changed, and why?
  5. Which tests ran?
  6. Where is the evidence?
  7. What did it cost?
  8. When the work changed hands, where did one agent stop and the next begin?

A commit message is not an answer. A green check is not an answer. “Done” is not an answer.

What is Praxis

Agents can write code. Praxis makes their work accountable.

Praxis is a repository-native work protocol. Work is captured, started, blocked, resumed and completed through one command-line interface, and every step is recorded next to the code it produced: which agent did it, in which execution, against which commits, with which evidence.

Done is a claim

Praxis interrogates it.

How it works

From intent, to execution, to evidence.

Every link in the chain is a record in the repository. Each one points to the next, so a finished piece of work can be followed back to why it started.

  1. Requirement

    The intent. An issue, a requirement record, a decision. Praxis records where work came from as its source reference.

    work capture --source-reference

  2. Work item

    A unit of work with a lifecycle: captured, ready, active, blocked, complete. The protocol refuses illegal transitions.

    work capture · work start

  3. Execution

    A record of one attempt at the work. Identity and repository baseline are recorded when it opens; its end and change summary when it is finalized.

    EXE-…

  4. Steps

    Starting, blocking, resuming and completing are events, appended to a log in the repository. Current versions record the actor that performed each one.

    work block · work resume

  5. Changes

    Changes since the execution’s starting baseline, committed or not, are summarized when it is finalized: files, lines, tests touched. If the baseline was dirty, the summary is marked unavailable.

    git

  6. Tests

    By default, completion requires naming an existing test file as evidence. Praxis checks the file exists; whether the tests pass is for CI to show.

    --evidence tests=…

  7. Evidence

    Completion names the files that prove the claim. The execution is then finalized and its record closed.

    work complete

  8. Reconciliation

    A commit made outside any work item can be assigned to one after the fact, explicitly and with a reason. Reconciliation never invents a work item.

    work reconcile

  9. Verified history

    Repository validation checks the records against each other and against Git.

    validate

Anatomy of an execution record

This is what one execution looks like when every source reports. The values are an example of layout, not a measurement: nothing in it came from a real run, and it is labelled so.

Every value carries its quality. Observed was reported by the runtime or the agent. Derived was calculated by Praxis from other records. Estimated is labelled as such, with its source. A value no source supplied is unknown or unavailable, never zero.

Git and Praxis

Git knows what. Praxis knows why.

Git is the record of change, and Praxis depends on it. Praxis keeps its own records in the same repository, in files Git versions like any other, and adds the context a diff was never meant to carry.

What Git establishes and what Praxis adds
Question Git establishes Praxis adds
What changed The exact content of every change, line by line. Summarizes the changes each execution made, measured from its starting baseline when that baseline was clean.
Who The configured author and committer of each commit. The actor behind the work: kind, provider, runtime, and model when it is reliably known.
Why The commit message, as written. The work item the change belongs to and the source it came from.
When Author and commit timestamps. When the work started, blocked, resumed and completed, and how long each execution ran.
Proof The history itself. The implementation and test evidence named at completion.
Handoffs Commits in sequence. Where one execution ended and the next began, and who ran each.

Agents

No anonymous work.

Agents, people and automation work under the same protocol. Each execution records who ran it, and how Praxis knows.

Identity

Actor kind, provider and runtime are detected from the runtime environment for OpenAI Codex, Claude Code, Gemini CLI, GitHub Copilot and GitHub Actions. They can also be declared explicitly, and a declaration takes precedence. The record keeps how provider and runtime were identified: from a known runtime environment, or explicitly or from an unmapped one.

Model

Recorded when the runtime reports it or it is declared. Otherwise it is recorded as unknown. Praxis does not infer a model from a provider.

Execution boundaries

Each execution has a start and a repository baseline, and an end once it is finalized. Blocking work does not close its execution, and resuming rejoins any execution still open. Once an execution is finalized, resuming opens a new one that points to it as its parent.

Telemetry, when it exists

Tokens, cost and runtime measurements are recorded when a runtime stream, hook, OpenTelemetry exporter or the agent itself supplies them. Every value keeps its source. Praxis does not compute cost; a cost calculated elsewhere must name its price table and version, and an estimate is labelled as one.

Every value says how it is known

Observed
Reported by the runtime, its telemetry, or the agent itself, with that source recorded.
Derived
Calculated by Praxis from other records, such as wall time from timestamps.
Estimated
Labelled as an estimate, with a confidence.
Unknown
No source could say. Recorded as unknown.
Unavailable
The runtime can report it, but nothing was supplied for this execution.

A missing value is never filled with a zero.

Integrity

The work continued. The identity was not assumed.

GH-84 is the issue for this website. Partway through, its first execution was blocked for a handoff and finalized, and the work was then resumed. These are the two executions exactly as Praxis recorded them, as of 2026-09-27.

parent

Blocking did not close the first execution; it was finalized explicitly, six seconds later. Because it was finalized, resuming did not reopen it. Praxis opened a new execution, linked it to the first as its parent, and identified the actor from the environment of the process that resumed the work, not from the record it continued.

The handoff note anticipated a different agent. That is not what happened: the same Claude Code session resumed the work. Both executions carry the same runtime session identifier, which the public snapshot deliberately leaves out. The record says what ran, not what was planned. No model was reported to either execution, and no token or cost telemetry reached either, so those say unknown.

Praxis will not transfer identity merely because the work continued.

Reconciliation

Every change has to answer for itself.

With attribution enforcement on, validation names a meaningful change that no work item accounts for and fails. The check is deliberately lenient while work is still open: when any work item is active or blocked, unattributed changes are not reported, and completing an item attributes the changes in the working tree to it.

  1. Attributed

    While the work happened

    The change was made under an active work item and is recorded with it.

  2. Reconciled

    After the fact, on the record

    work reconcile assigns committed changes to a real work item using Git history as the evidence, with a stated reason. The record says permanently that attribution came later. Nothing is backdated.

  3. Unresolved

    Until someone can say

    If nobody can honestly name the work item, the change stays unresolved, and validation reports it whenever no work is open.

Reconciliation fails closed. It will not create a work item, sweep in unrelated history, assign a merge commit, reach past a shallow clone, or overwrite a change already reconciled elsewhere. When the evidence is not reliable, it records nothing.

Manufactured attribution is worse than explicitly unresolved attribution. Touching files to make them look attributed destroys the history of who changed what. Praxis gives no reason to do it.

Resilience

The process survives the tool.

An engineering record that exists only while one program is running is not a record. Praxis keeps the record in files, so the obligation outlives any agent, runtime or version of Praxis itself.

Available now

  • Work state, events, executions and provenance are plain JSON and JSON Lines files in the repository. Any tool can read them; Git versions them.
  • Validation re-checks the records against each other and against Git history, in CI, independent of whoever wrote them.
  • Changes committed without a work item can be reconciled later, from Git history, on the record.
  • A finalized execution is closed. Continuing the work opens a new one rather than reopening the old.

Architectural direction

  • Double-entry execution: when the Praxis CLI cannot run, an agent writes a conforming fallback execution record by hand.
  • CI later reconciles fallback records against Git and the protocol, and accepts or rejects them on evidence.

Not implemented. Not scheduled. This is the direction the record format is designed to allow, stated so nobody mistakes it for a feature.

Repository-native

The record lives with the code.

Praxis records are ordinary files next to the source they describe. Where evidence lives somewhere else, such as an issue, a pull request or a CI run, the record points to it by reference.

Versionable
Every record is a file in the repository. It branches, merges and reverts with the code.
Inspectable
JSON and JSON Lines. Open them in an editor, diff them in a pull request, query them with anything.
Portable
No server and no account. Clone the repository and the record comes with it.
Attributable
Events written by current versions carry the actor that caused them; each execution carries the identity that ran it.
Reviewable
Changes to the record appear in the same pull request as the changes to the code.
Automatable
A single CLI with machine-readable output, run the same way by people, agents and CI.

Independence

Useful on its own. Stronger in the foundry.

Praxis needs a Git repository and nothing else. It is part of Echelon Foundry, and it connects to other Echelon tools where they exist, but none of them is required.

Available now

  • Standalone. Install it into any Git repository. No server, account or other Echelon tool.
  • External work systems. A transport-neutral adapter contract through which an adapter reads and transitions work items in an external tracker, reporting conflicts instead of overwriting either side. The contract ships; tracker-specific adapters are yours to write.
  • Ordo. Praxis can record Ordo decisions and their later outcomes, and package handoff context, without becoming Ordo’s authority.
  • Echelon bootstrap. The native bundle includes echelon, which reports which Echelon tools are present and whether the environment is coherent.

Architectural direction

  • Deeper integration with other Echelon Foundry systems. Some have requirements written; none is integrated beyond what is listed as available.

Direction, not a feature list. When an integration ships, it moves to the other column.

    A claim is where verification starts, not where it ends. Completion requires evidence.

Get started

Put a repository under Praxis.

Native bundles for macOS, Linux and Windows. No Node.js, npm or machine-wide .NET runtime is required.

1 Install

macOS or Linux:

curl -fsSL https://raw.githubusercontent.com/kemiller2002/praxis/main/scripts/install-native.sh | sh

Windows PowerShell:

irm https://raw.githubusercontent.com/kemiller2002/praxis/main/scripts/install-native.ps1 | iex

Read the installers before you pipe them to a shell: install-native.sh, install-native.ps1. Each downloads the latest release bundle and checks it against the published checksums.

2 Initialize a repository

$ cd your-repository
$ praxis init
$ praxis status
$ praxis verify

3 Read the protocol

The work protocol, the CLI reference and the agent contract are in the repository: work protocol, CLI reference, native installation.

From ROS to Praxis

Praxis was previously named ROS, the Repository Operating System. The rename is in progress, and both names are in use today:

  • The native installer provides praxis, and keeps ros as an alias for the same program.
  • The npm package @echelon-foundry/repository-operating-system still provides only ros: npx --package=@echelon-foundry/repository-operating-system ros init.
  • init adds a repository-local ./ros launcher. It runs on Node.js; the installed praxis command does not need Node.
  • Help text and some output still say ROS.

Same tool, same records. Commands on this page use praxis; wherever you have ros, the arguments are identical.

Checked The commands in step 2 were run against release v3.4.0 on Linux x64, after verifying the bundle’s checksum. Other platforms were not tested for this page.

What the record caught

Commit 588599e in this site’s history is titled as the completion of PRAXIS-SITE-15. The completion had in fact failed on a malformed argument. The Praxis record still showed the item active, and the next commit, 6d7b300, records the real completion and says why. The commit message made a claim; the record did not agree; the record was right.

What this page does not claim

Deployment is not a Praxis record, so it is not in the ledger. When this snapshot was taken the site had not been deployed. If you are reading it on the web, deployment happened afterwards, and its record is the GitHub Actions run that published it.
